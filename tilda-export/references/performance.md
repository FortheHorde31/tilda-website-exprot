# Скорость: от разбора HTML до проверки публикации

Эта проверка входит в каждый перенос. Сначала исследуй исходник, затем применяй
нужные изменения при сборке блоков. Не запускай отдельный редизайн ради скорости.
Сохраняй текст, функции, выбранные шрифты и геометрию. Уже исправленный пункт
не записывай как новую оптимизацию.

## 1. Исходник и план

До правок сохрани исходные файлы и хэши. Проверь первый экран, изображения,
шрифты, CSS, JS, iframe и внешние домены. Если браузер доступен, определи фактический
LCP и его ресурс. Без замера помечай элемент как кандидат, а не установленный LCP.
Первый экран может содержать текст, а не изображение. Не назначай preload картинке
только потому, что это первая картинка в HTML.

Создай `performance-plan.json`: находки и для каждой — действие, причина,
статус (applied / retained / deferred / not-applicable), способ проверки.
Запиши исходные и новые пути ресурсов, если они меняются. Не выдавай предположение
о влиянии за доказанный выигрыш в миллисекундах.

## 2. Правила сборки

| Объект | Действие |
|---|---|
| LCP-изображение | Не ставь lazy. Проверь fetchpriority=high. Preload добавляй при позднем обнаружении и подтверждённой необходимости; URL, srcset/sizes и CORS должны соответствовать реальному запросу. Не загружай две версии картинки из-за несовпадения подсказок |
| Шрифты | Убери повторные подключения и поздние @import из секций. Подключай общий шрифт в HEAD. Для собственных файлов предпочитай WOFF2, нужные начертания/наборы, font-display: swap. Проверь сдвиг текста при замене fallback. Сохрани исходный шрифт |
| Preload шрифта | Только нужный первому экрану файл, а не все веса и языки. Для font используй as=font, type=font/woff2 и crossorigin. Набор символов выбирай по языку страницы; кириллица и Inter не универсальны. Лицензия должна разрешать выбранный способ размещения |
| Изображения | Проверь размеры показа и реальный вес ответа CDN. WebP/AVIF применяй только при уменьшении загрузки и приемлемом качестве. Не перекодируй автоматически SVG, анимацию и уже оптимизированные файлы. Маленькие иконки можно оставить встроенными; большие base64 оцени отдельно |
| CLS | Задавай width/height или CSS aspect-ratio. Резервируй место под iframe, видео и виджеты. Проверь загрузку шрифтов и контента в браузере: атрибуты сами по себе не гарантируют отсутствие сдвигов |
| Ниже первого экрана | Добавляй lazy подходящим картинкам и iframe, если это сохраняет поведение. Не откладывай элементы первого экрана и не меняй триггеры виджетов вслепую |
| Preconnect | Только несколько реально критичных HTTPS origins, без пути/параметров. Нужный CORS-режим зависит от ресурса. Не подключай заранее все домены страницы |
| CSS/JS | Убирай подтверждённые дубли. Общие ресурсы загружай один раз, отражай зависимости в манифесте. Async/defer применяй только с учётом порядка исполнения. Сохраняй 3D, формы, cookie-логику и аналитику |

Для общего HEAD создай `head.html`, укажи `head_file` в манифесте. Это фрагмент
для добавления к существующему HEAD, не весь документ. Генератор превью вставляет
его в HEAD до блоков — локальная и удалённая страницы используют один код.
Не вырезай @import, пока нужное подключение не перенесено и не проверено.

## 3. Локальная проверка

`check_export.py` включает статический аудит из `scripts/performance.py`.
Он сообщает о подозрениях: lazy у явно отмеченного LCP, отсутствии размеров в HTML,
@import шрифтов, повторах ресурсов, неверных font preload, избытке подсказок и
скриптах без признаков отложенной загрузки. Предупреждения требуют решения агента,
не блокируют экспорт сами по себе и не означают установленную причину торможения.
CSS, JS, состояние первого экрана и ресурс из srcset требуют браузера.

Необязательные поля манифеста:

```json
{
  "head_file": "head.html",
  "performance": {
    "lcp": {"kind": "image", "src": "https://example.com/cover.webp", "status": "candidate"}
  }
}
```

У картинки можно вместо src добавить `data-performance-role="lcp"`.
Для текста запиши `kind: "text"`, `selector` и основание в performance-plan.json.
Манифест не добавляет атрибуты в HTML автоматически. Отсутствие lcp не доказывает,
что аудит первого экрана сделан. `performance.manual_checks` всегда остаются
открыты до отдельного браузерного отчёта.

## 4. Загрузка MCP и замер

При порученной загрузке сначала сохрани текущий HEAD. Объедини его с новым
без потери метаданных, счётчиков, CSP и существующих подключений. Если нужен
не весь head.html, явно сохрани итоговую версию. Прочитай запись обратно, проверь
содержимое и подключение ресурсов. Отправка блоков не заменяет отправку HEAD.

После порученной публикации проверь фактическую версию и сеть: нужный шрифт,
один запрос критичного ресурса, отсутствие сдвигов, работу CTA/попапов/анимации.
Не публикуй страницу только ради замера без поручения.

Сравни исходник и результат в одинаковой среде. Используй чистый профиль без
расширений, одинаковые viewport, сеть, CPU и версии инструментов. Для оценки
скорости сделай несколько чередующихся запусков и сравни медианы. Для Lighthouse
укажи FCP, LCP, CLS, TBT и Performance. TBT не является измерением INP.
Не называй локальные замеры Production PageSpeed или полевыми Core Web Vitals.
При ошибках ресурсов/замера, предупреждениях Lighthouse или отсутствии исходного
контроля опиши ограничения и не заявляй причинный эффект.

## 5. Ограничения и отчёт

Не удаляй штатные tilda-grid/скрипты, аналитику, cookie-логику и защитные механизмы
ради балла. HTML не меняет cache headers чужого сервера. Серверное встраивание
CSS не относится к обычному Tilda MCP; не переноси такой эксперимент в этот путь.
Не меняй весь проект ради одной страницы и не обещай 90–100 баллов.

Сдай `performance-report.md` или JSON: что найдено, что исправлено, что сохранено
и почему, какие проверки сделаны, результаты и оставшиеся ограничения.
Если были только статические проверки, прямо укажи: скорость не измерена.
